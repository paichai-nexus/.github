# 🧩 NEXUS System

<p align="center"><img src="https://raw.githubusercontent.com/paichai-nexus/.github/main/assets/nexus-workflow-v7.png" width="100%" alt="NEXUS workflow"></p>

<table><tr>
<td width="20%" valign="top"><h3>01 · DISCOVER</h3><b>문제를 찾습니다.</b><br><br>현장의 불편, 연구 질문, 사용자 요구에서 기술적으로 풀 가치가 있는 문제를 발견합니다.</td>
<td width="20%" valign="top"><h3>02 · DEFINE</h3><b>역할을 정의합니다.</b><br><br>문제를 전공별 관점으로 분해하고 누가 무엇을 책임질지 명확히 합니다.</td>
<td width="20%" valign="top"><h3>03 · BUILD</h3><b>실제로 만듭니다.</b><br><br>프로토타입, 코드, 실험 설계, 디자인, 문서 등 확인 가능한 산출물을 만듭니다.</td>
<td width="20%" valign="top"><h3>04 · VALIDATE</h3><b>검증합니다.</b><br><br>사용자, 전문가, 데이터, 실험을 통해 주장과 실제 결과를 구분합니다.</td>
<td width="20%" valign="top"><h3>05 · EVIDENCE</h3><b>근거를 남깁니다.</b><br><br>다음 사람이 재현하고 이어갈 수 있도록 결정과 한계, 결과를 기록합니다.</td>
</tr></table>

## Delivery Pipeline
```text
Problem / Question
        │
        ▼
DISCOVER
현장 · 사용자 · 연구 질문
        │
        ▼
DEFINE
전공별 역할 · 범위 · 성공 기준
        │
        ▼
BUILD
Prototype · Research · Software · Hardware · Design
        │
        ▼
VALIDATE
Expert Review · User Test · Data · Experiment
        │
        ▼
EVIDENCE
Docs · Repository · Report · Presentation · Paper
        │
        ▼
NEXT
Competition · Service · Research · Collaboration · Handover
```

## Quality Gates
<table><tr>
<td width="25%" valign="top"><h3>G0 · IDEA</h3>아이디어가 흥미로운가?<br><br><b>아직 성과가 아닙니다.</b></td>
<td width="25%" valign="top"><h3>G1 · BUILD</h3>실제로 작동하는가?<br><br><b>구현 여부를 확인합니다.</b></td>
<td width="25%" valign="top"><h3>G2 · VALIDATE</h3>의도한 문제를 해결하는가?<br><br><b>사용자·전문가·데이터로 검증합니다.</b></td>
<td width="25%" valign="top"><h3>G3 · EVIDENCE</h3>다른 사람이 재현할 수 있는가?<br><br><b>근거와 한계를 남깁니다.</b></td>
</tr></table>

<p align="center"><b>구상 ≠ 구현 ≠ 시연 ≠ 검증 ≠ 실증</b><br>NEXUS는 각 단계를 구분하고, 과장보다 기록을 선택합니다.</p>

# 🧠 Principles

<table><tr>
<td width="33%" align="center"><h1>BUILD</h1><h3>말보다 결과물</h3>아이디어를 설명하는 데서 멈추지 않고 실제로 확인할 수 있는 것을 만듭니다.</td>
<td width="33%" align="center"><h1>VALIDATE</h1><h3>주장보다 검증</h3>“가능성 있다”와 “확인했다”를 명확히 구분합니다.</td>
<td width="34%" align="center"><h1>CONNECT</h1><h3>전공보다 연결</h3>전공의 경계를 지키기보다 문제 해결에 필요한 역할을 연결합니다.</td>
</tr></table>

### Our rules
- **아이디어를 성과처럼 말하지 않습니다.**
- **데모와 검증을 구분합니다.**
- **전문가 판단이 필요한 영역을 기술이 대체했다고 주장하지 않습니다.**
- **프로젝트의 한계도 결과의 일부로 기록합니다.**
- **누가 무엇을 했는지 역할을 명확히 남깁니다.**
- **다음 팀이 다시 처음부터 시작하지 않도록 문서화합니다.**

> ### 결과물은 보여주고, 판단은 검증하며, 과정은 기록합니다.

<details><summary><b>💬 어떤 사람이 잘 맞나요?</b></summary>

NEXUS는 “이미 잘하는 사람”만을 위한 조직이 아닙니다.

- 자신의 전공을 다른 분야와 연결해보고 싶은 사람
- 프로젝트에서 실제 역할을 맡아보고 싶은 사람
- 질문하고, 배우고, 기록할 수 있는 사람
- 결과가 예상과 달라도 원인을 함께 분석할 수 있는 사람
- 다른 전공의 언어를 이해하려 노력하는 사람
- 발표, 디자인, 조사, 운영 역시 프로젝트의 핵심이라고 생각하는 사람
</details>

<details><summary><b>🧪 개발 경험이 없어도 되나요?</b></summary>

가능합니다. NEXUS 프로젝트에는 개발 외에도 기획, 사용자 조사, 디자인, 도메인 지식, 실험, 운영, 문서화, 발표, 대외협력 등 다양한 역할이 필요합니다.

중요한 것은 **“내 전공으로 이 프로젝트에 무엇을 기여할 수 있는가”를 함께 찾는 것**입니다.
</details>

<details><summary><b>📚 프로젝트 경험이 없어도 되나요?</b></summary>

가능합니다. 초기에는 작은 역할부터 시작하고 프로젝트 기록과 기존 산출물을 보면서 업무 방식을 익히는 구조를 지향합니다.

NEXUS의 장기 목표 중 하나는 **새로운 사람이 들어와도 조직이 다시 처음부터 시작하지 않는 구조**를 만드는 것입니다.
</details>
